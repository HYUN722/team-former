# 구현 계획

## 1. 파일 구성

```
├── streamlit_app.py      앱 본체 (화면)
├── db.py                 DB 연결과 질의
├── rules.py              팀 규칙 검사 (순수 함수, 화면/DB와 무관)
├── ai_assign.py          오픈라우터 호출과 3중 폴백, 완전 탐색 배정
├── schema.sql            테이블 생성 SQL
├── requirements.txt
├── .gitignore            .env 를 반드시 포함
├── .env                  (깃허브에 올리지 않음)
├── README.md
├── docs/
│   ├── PRD.md
│   └── 구현계획.md
├── data/                 연습용 시나리오 CSV 3개
└── img/                  README에 넣을 화면 캡처
```

규칙 검사를 `rules.py` 로 떼어 내는 이유: 지원 시점 검사, 승인 직전 재검사, AI 배정안 검사가 **같은 규칙**을 쓴다. 한 곳에 모아야 세 군데가 어긋나지 않는다.

## 2. 데이터 모델

`schema.sql` 참고. 핵심은 DB가 스스로 지켜 주는 제약이다.

| 제약 | 막아 주는 것 |
| --- | --- |
| `tf_members (team_id, slot_no)` 기본 키 | 같은 자리에 두 명 (동시 지원) |
| `tf_members.student_id` 유일 | 한 학생이 두 팀에 소속 |
| `slot_no between 1 and 4` | 5번째 자리 |
| `main_role`, `role` 의 `check (... in (...))` | 역할 6개 밖의 값 |
| `tf_applications` 부분 유일 인덱스 (`status='대기'`) | 한 학생이 동시에 두 곳에 지원 |
| `tf_votes (application_id, voter_id)` 기본 키 | 같은 지원에 두 번 투표 |

## 3. 단계별 구현

### 1단계 — 뼈대와 로그인
- `db.py`: `st.connection` 또는 psycopg 연결을 `@st.cache_resource` 로 한 번만 만들기
- 앱 시작 시 `ADMIN_PASSWORD` 로 admin 계정 생성/갱신
- bcrypt 해시 저장, 로그인 검증
- `whoami`, `result` 컨테이너 틀
- 학생 계정으로 관리자 화면에 못 들어가게 막기 (감점 11번)

### 2단계 — 관리자 명단 올리기
- CSV를 `utf-8-sig` 로 읽기 (BOM 대응)
- 지원·투표·팀원·마감 표시 삭제 → 학생과 빈 팀 재생성, admin 계정은 유지
- `sub_roles` 는 `;` 로 분리, 빈 값 허용
- 결과 안내는 "승인: …" / "막힘: …"

### 3단계 — 팀 목록과 지원
- 팀마다 `team_N` 컨테이너, 팀원 이름·주 역할·보조 역할 표시, 내 팀 구분
- `apply_N` 단추 — 이미 팀 있음 / 대기 지원 있음 / 마감 → 단추 숨김
- 그 밖의 막힘(꽉 참, 주 역할 중복, 필수 포함 역할 자리)은 `rules.can_apply()` 로 판정해 "막힘: 이유"
- 팀원이 없으면 즉시 승인, 있으면 대기

### 4단계 — 투표와 승인 직전 재검사
- 지원마다 `vote_yes_{학번}`, `vote_no_{학번}`
- 거부 1표 → 즉시 거절
- 전원 찬성 → `rules.check_approval()` 재검사 → 통과 시 승인, 실패 시 "거절: …"
- 투표자 집합은 **투표하는 시점의 팀원**
- 이미 투표했으면 단추 숨기고 내 투표 표시

### 5단계 — 마감
- 대기 지원 전부 거절
- 1명 팀의 학생을 팀에서 제거
- `unassigned` 에 팀 없는 학생 이름 표시

### 6단계 — AI 배정
- 먼저 `rules.feasible()` 로 규칙을 지키는 배정이 존재하는지 확인. 없으면 AI를 부르지 않고 `assign_status` 에 이유 표시
- 있으면 1차 → 2차 → 3차 모델 순차 호출
  - 모델마다 전체 대기 120초 (스레드 + `concurrent.futures` 의 `timeout`)
  - `reasoning effort: low`, `max_tokens` 넉넉히 → 빈 응답 줄이기
  - 응답 JSON 파싱 실패/빈 응답/오류/검사 실패 → 다음 모델
  - 진행 상황을 `assign_status` 에 "1차 모델 응답 대기 중" 처럼 표시
  - 호출 결과를 `tf_ai_logs` 에 기록 (README 사례 근거로 씀)
- 3차까지 실패 → 완전 탐색(백트래킹)으로 5가지 검사를 모두 통과하는 배정 찾기
- 통과한 배정안만 표로 보여 주고 `admin_confirm` 으로 DB 저장

### 7단계 — 자동 갱신
- 팀 목록과 지원 목록을 `@st.fragment(run_every="3s")` 로 감싸 다른 사람의 변경이 자동으로 보이게 함
- 채점 프로그램은 단추를 7초까지 기다리므로 3초면 충분

### 8단계 — 배포와 마무리
- 비공개 저장소 → Streamlit 연결 → Secrets 입력 → 앱 공개로 전환 → 시크릿 창 확인
- 연습 시나리오 3개 실행, 화면 캡처 수집
- README 작성

## 4. 핵심 알고리즘

### 4.1 필수 포함 역할 자리 계산

팀의 학생 집합에서 "기획자를 맡을 수 있는 사람"과 "웹 프로그래머를 맡을 수 있는 사람"을 **서로 다른 사람으로** 고를 수 있는 최대 개수를 센다(사람 2명, 역할 2개짜리 이분 매칭이므로 경우의 수를 직접 따져도 된다).

```
충족한 필수역할 수 = max_matching(팀원들, {기획자, 웹 프로그래머})
남은 필수역할 수 = 2 - 충족한 필수역할 수
지원자를 넣은 뒤 남는 자리 = 4 - (현재 인원 + 1)
if 남는 자리 < 지원자를 넣은 뒤의 남은 필수역할 수: 막음
```

예) 테스터와 발표자만 있는 2명 팀에 보고서 작성자가 지원 → 넣으면 3명, 남는 자리 1개, 아직 필수역할 2개 필요 → 막음.

### 4.2 승인 직전 재검사

전원 찬성이 모인 순간 다시 검사한다. 순서가 중요하다 — 같은 팀에 대기 지원이 여럿일 때 **투표가 먼저 끝난 지원**이 먼저 처리되고, 뒤 지원은 바뀐 팀 상태로 검사받는다. (어려움 시나리오 6~8단계가 정확히 이 경우다.)

### 4.3 완전 탐색 배정

팀 없는 학생이 최대 8명, 팀이 3~4개이므로 경우의 수는 작다. 학생을 하나씩 팀에 넣어 보되, 넣는 즉시 정원·주 역할 중복을 검사해 가지치기하고, 전부 넣은 뒤 인원(2~4명)과 필수 포함 역할을 검사한다. 첫 해를 찾으면 멈춘다.

## 5. 테스트 계획

연습 시나리오 3개를 앱에서 직접 실행하고, 각 단계의 `result` 첫 단어가 기대 결과와 같은지 확인한다.

| 시나리오 | 특히 확인할 것 |
| --- | --- |
| 쉬움 | 기본 흐름, 거부 1표로 즉시 거절(4단계), 배정과 확정 |
| 중간 | 주 역할 중복 막힘(3단계), 한 번에 한 팀(8단계), 마감 처리(9단계), 마감 뒤 지원 막힘(10단계) |
| 어려움 | 승인 직전 재검사(8단계), 필수 포함 역할 자리 막힘(11단계), 마감 때 1명 팀 해체(14단계) |

브라우저 창을 여러 개(시크릿 창 포함) 띄워 학생별로 로그인해 시험한다.
